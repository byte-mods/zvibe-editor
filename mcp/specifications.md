# Babylon.js Editor MCP specifications

This document records cross-client behavioral contracts that are not fully expressed by JSON Schema alone. Tool schemas and descriptions in `mcp/src/tools` remain the executable contract.

## Portable ML-Agents-style training contract (#764)

Scene metadata uses the versioned `zvibe-ml-training-v1` contract. Each behavior binds one or more exact scene Agent node ids, one or more bounded vector-observation specifications with stacking, continuous and/or discrete action branches, a decision period, maximum episode steps, optional inference-model path, optional Behavior Graph id, and deterministic behavior mode. Curriculum lessons retain exact thresholds and scalar parameters. Generated games configure `MlTrainingRuntime`, whose public bridge requests decisions, accepts rewards, ends episodes, exposes state, and can be connected to a user-controlled trainer handler without importing editor code.

Demonstration episodes are normalized against the selected behavior and retained in a project-private bounded dataset. Provider manifests persist only executable argv, supported algorithms, duration, and credential environment-variable names. The built-in provider performs genuine deterministic linear behavior cloning and emits an ONNX `Gemm` policy. External providers execute without a shell, receive one JSON request over standard input, stage `policy.onnx`, and return bounded JSON metrics over standard output. One Editor owner enforces 10,000 episodes, 100,000 steps, 32 MiB dataset size, 32 retained jobs, four queued jobs, one concurrent process, 256 MiB model size, bounded diagnostics/metrics, timeout, cancellation, retry-as-new-job, exact revisions/fingerprints, project identity, and shutdown termination. Every accepted ONNX model must expose compatible float32 rank-two observation/action tensors with exact feature dimensions.

Checkpoint publication requires the exact terminal job revision, result fingerprint, destination inspection fingerprint, and literal confirmation. It publishes only project-contained `.onnx` assets, refuses symbolic paths, transactionally preserves collisions, writes normal AI Model metadata and non-secret training provenance, refreshes the normal asset registry, and compiles the result through Runtime AI before commit; failure restores every prior artifact. Generic asset deletion removes the provenance sidecar.

The eighteen strict tools are `get_ml_training_capabilities`, `get_ml_training_configuration`, `set_ml_training_configuration`, `list_ml_training_providers`, `set_ml_training_provider`, `delete_ml_training_provider`, `record_ml_training_episode`, `list_ml_training_episodes`, `get_ml_training_episode`, `clear_ml_training_dataset`, `start_ml_training_job`, `list_ml_training_jobs`, `get_ml_training_job`, `cancel_ml_training_job`, `retry_ml_training_job`, `inspect_ml_training_checkpoint_publication`, `publish_ml_training_checkpoint`, and `delete_ml_training_job`. Every schema is nested-closed and bounded and every tool publishes all four annotations for Codex CLI and Claude-compatible clients. This is portable provider-neutral behavior; it does not claim Unity ML-Agents Python package/API, Barracuda/Sentis training identity, distributed-training infrastructure, or learned-policy quality equivalence.

## Integrated generative asset creation contract (#763)

One provider-neutral version-1 request/result contract covers image, sprite or sprite-sheet, PBR material-map set, animation clip, and audio candidates. Providers are explicitly classified as `generative-ai`, `procedural`, or `test-fixture`; only a real executed provider classified `generative-ai` may be reported as generative AI. The Editor bundles no model or provider. Executable providers receive one JSON request over standard input and return JSON over standard output without a shell. HTTP providers must use HTTPS, except loopback development endpoints, and credentials are resolved at execution time from a configured environment-variable name that is never serialized with its value or returned in logs/results.

One Editor-lifetime owner retains a bounded paginated job queue, enforces global and provider concurrency, input/output byte and artifact limits, timeout, cancellation, revision, project identity, and terminal-result retention, and cancels active work on project switch or Editor shutdown. Retry creates a new job linked to its source rather than mutating historical evidence. Validation rejects malformed media, dimensions, frame/sample/key limits, non-finite animation values, unsafe names/paths, mismatched declared hashes, or modality-incompatible artifacts before preview or publication.

Publication first produces an exact candidate/source/settings/project fingerprint and a collision-safe project-relative plan. Applying that plan requires the exact fingerprint and literal confirmation. Image and sprite candidates use the normal texture importer; audio and animation use their ordinary asset forms; material sets publish validated maps, a Babylon PBR material, and packed ORM where requested. Source files, metadata sidecars, GUID/importer caches, provenance, and history are one transaction and are restored on any failure. Published metadata records provider id/classification, job and candidate ids, prompt hash rather than secret content, output hashes, request contract, and timestamp.

The thirteen strict tools are `get_generative_asset_capabilities`, `list_generative_asset_providers`, `set_generative_asset_provider`, `delete_generative_asset_provider`, `start_generative_asset_job`, `list_generative_asset_jobs`, `get_generative_asset_job`, `cancel_generative_asset_job`, `retry_generative_asset_job`, `get_generative_asset_preview`, `inspect_generative_asset_publication`, `publish_generative_asset_candidate`, and `delete_generative_asset_job`. Every schema is nested-closed and bounded and every tool publishes all four annotations for Codex CLI and Claude-compatible MCP clients. This does not claim Unity Muse/Asset Manager package, service, model, billing, serialization, API, or output identity.

## Portable FBX export and round-trip contract (#762)

FBX export accepts either the complete live Babylon scene or 1–256 exact case-sensitive root node ids. Node exports include descendants by default, cap the resolved scope at 10,000 unique nodes, and temporarily replace excluded ancestors with transform-only shells so selected world transforms survive without leaking ancestor mesh geometry. The shells are always restored. The inspected in-memory GLB v2 snapshot, exact scope, destination, and normalized settings produce one lowercase SHA-256 lease; node evidence is independently paginated.

Destinations must be ordinary project-relative `.fbx` files below `assets/` and may not traverse or follow symbolic-link path segments. Export requires the exact inspection fingerprint and literal `confirm=true`. The editor invokes configured or installed Blender with an argv array rather than a shell, bounds source/output bytes, time, logs, and settings, validates the binary FBX header/version plus exact source/output hashes, and reserializes the live scene after conversion. Any stale scene, changed settings/path/project, missing Blender, timeout, malformed evidence, or publication failure preserves the previous complete asset/evidence pair. Same-destination writes are serialized while distinct destinations may convert concurrently. Generic asset deletion fences active exports, blocks later exports until cleanup completes, and removes the hashed private FBX evidence together with normal importer artifacts.

Round-trip first applies the same exact export. It then uses the ordinary model-importer artifact pipeline and ordinary mesh-asset instantiation owner, so FBX reimports receive the same dependency, material, animation, hierarchy, selection, save/export, and cleanup behavior as other supported model assets. A later importer or instantiation failure does not invalidate an already verified FBX publication; repeated successful round-trip calls intentionally create additional scene instances.

The four strict tools are `get_fbx_export_capabilities`, `inspect_fbx_export`, `export_fbx_asset`, and `round_trip_fbx_export`. Capability and inspection calls are read-only/idempotent. Export is destructive/idempotent for one exact destination and lease. Round-trip is destructive/non-idempotent because it creates a scene instance. Every schema is closed and bounded and every tool publishes all four annotations to Codex CLI and Claude-compatible clients.

This is portable Babylon/Blender FBX authoring behavior. It does not claim Unity FBX Exporter package/API/serialization identity, Autodesk SDK identity, or byte-identical output across DCC versions.

## Portable Aseprite import, sprites, and animation contract (#761)

Project-contained `.ase` and `.aseprite` files remain the authoring source. One bounded native parser covers indexed, grayscale, and RGBA documents; normal, group, image, and tilemap hierarchy; raw, linked, and zlib-compressed cels; embedded and project-contained external tilesets; frame duration, opacity, visibility, z-index, user data, all 19 Aseprite blend modes, animation tags, slices, pivots, and nine-patch centers. Unknown chunks are skipped within their declared frame span. Recursive external files, compressed expansion, dimensions, pixels, layers, cels, frames, tiles, events, and atlas work are all bounded before publication.

Import inspection hashes the exact source, normalized settings, and recursively resolved external tileset bytes. Apply requires that exact lowercase SHA-256 fingerprint plus literal confirmation and atomically publishes `atlas.png`, `atlas.json`, and `aseprite-import.json`; a stale lease, malformed input, missing/substituted dependency, traversal, cycle, limit failure, or write failure cannot replace a current artifact partially. Potentially large dependency, layer, tag, slice, tileset, and frame collections are independently paginated.

A current artifact instantiates as either one composite SpriteManager or a mirrored group/layer hierarchy when `layerMode="compositeAndLayers"` was imported. Generated sprites retain exact variable frame timing, forward/reverse/ping-pong direction, finite/infinite repeat, pixel aspect, pivots, trimmed local transforms, empty-frame visibility, and bounded cel events. The root stores exact source/import provenance and a positive revision. Animation control identifies exactly one root, requires its current revision, and changes every composite/layer stream atomically; a failed stream restores them all. Pause retains the current cursor, stop rewinds, seek requires an exact frame plus an in-frame elapsed offset, unfinished clips resume, and completed finite clips restart. Confirmed deletion removes only the instantiated hierarchy, not the source or importer artifact.

The eight strict tools are `get_aseprite_capabilities`, `inspect_aseprite_import`, `apply_aseprite_import`, `instantiate_aseprite_asset`, `list_aseprite_instances`, `get_aseprite_instance`, `control_aseprite_animation`, and `delete_aseprite_instance`. All schemas are closed, bounded, and project-contained; reads paginate large tables; artifact replacement and deletion require literal confirmation; playback requires an exact revision; and every tool publishes all four safety annotations to Codex CLI and Claude-compatible MCP clients.

This is portable Aseprite/Babylon.js behavior. It does not claim Unity 2D Aseprite Importer package/API/serialization identity, Aseprite application automation, Unity Sprite Library/Sprite Resolver identity, or bit-identical Unity sprite packing and rendering.

## Portable Alembic import and playback contract (#760)

Missing Blender, changed leases, malformed archives, limit failures, or unrelated converter output publish nothing.

The shared Babylon/JavaScript runtime reconstructs sampled meshes with face-set material slots, points, curves, cameras, visibility and optics. Full scenes, additive scenes, editor preview and exported Web/Desktop players use the same owner; generated players require no Blender dependency.

Every schema is closed and bounded, publishes all four annotations, and is shared by Codex CLI and Claude-compatible MCP clients.

This is portable Alembic authoring/playback behavior for Babylon.js. It does not claim Unity Alembic package/API/serialization identity, proprietary DCC integration, arbitrary Python execution, or bit-identical renderer output.

## Unity-style Occlusion Culling contract (#758)

One closed version-1 scene record owns enablement, exact configuration and bake revisions, bounded Unity-facing settings, up to 256 axis-aligned Occlusion Areas/View Volumes, and at most one atomically published bake. Per-mesh records independently author Static Occluder, Static Occludee, and Babylon hardware-query policy; per-camera records independently enable baked PVS use. Only enabled opaque triangle meshes at or above Smallest Occluder can block static rays. Dynamic query meshes can be occludees but never contribute static occlusion.

The portable `bounded-static-pvs-ray-bake-v1` owner divides authored areas—or one conservative derived scene volume—into at most 4,096 cells. It uses bounded view/target samples, a five-ray Smallest Hole clearance bundle, geometric-winding Backface Threshold evidence, and at most 2,000,000 ray tests plus 2,000,000 cell-to-mesh relationships. Inspection validates every source and returns an exact SHA-256 source lease. Bake revalidates that lease before and after work, yields between cells, and publishes only a complete fingerprinted result. Cancellation, stale configuration, changed mesh/material/transform sources, unsupported opaque evidence, or work-limit failure publishes nothing.

Editor preview, full exported loading, and additive-scene composition use one runtime owner. Immediately before each configured camera, the runtime selects a containing valid baked cell and temporarily hides only its exact baked occludees; immediately after that camera it restores every authored visibility value. Missing/stale bakes, invalid Backface Threshold cells, cameras outside all cells, missing source meshes, or changed source signatures fail open and preserve visibility. Additive scenes retain independent configuration sets instead of merging unrelated cell ids. Native Babylon occlusion queries supplement dynamic occludees when the engine reports support and are restored exactly on reconfiguration/disposal.

The permanent workspace exposes Unity-style Object, Bake, and Visualization tabs. Visualization uses transient non-pickable, non-serializing line meshes and can display cells plus one selected cell's visible/occluded source bounds. Reads expose exact job progress, bake statistics, stale evidence, and per-camera runtime decisions. Scene serialization/export retains authored scene/mesh/camera records and bake data while excluding transient debug geometry.

The fifteen tools are `get_occlusion_culling_capabilities`, `get_occlusion_culling`, `set_occlusion_culling_settings`, `set_occlusion_culling_mesh`, `set_camera_occlusion_culling`, `create_occlusion_culling_area`, `update_occlusion_culling_area`, `delete_occlusion_culling_area`, `inspect_occlusion_culling_bake`, `bake_occlusion_culling`, `cancel_occlusion_culling_bake`, `clear_occlusion_culling_bake`, `get_occlusion_culling_runtime`, `set_occlusion_culling_visualization`, and `reset_occlusion_culling`. Every schema is nested-closed and bounded and publishes all four annotations. Mutations use exact configuration/object/job/source/bake leases; area deletion, bake clearing, and complete reset require literal confirmation. The server exposes 1,664 tools to Codex CLI and Claude-compatible clients. This is conservative portable Babylon/JavaScript behavior, not Unity/Umbra API, serialization, binary, or numerical identity.

## Portable Runtime AI inference contract (#756–#757)

`.onnx`, `.tflite`, and `.pt2` files use the version-1 `aiModel` importer. Its settings select `automatic`, `wasm`, or `webgpu`; graph optimization; sequential/parallel execution; CPU allocation reuse; Wasm worker count; WebGPU layout/validation; the per-tensor element ceiling; and build inclusion. ONNX uses ONNX Runtime Web. LiteRT uses official `@litertjs/core`; its synchronous compiled-model invocation cannot be interrupted, so its bounded deadline is checked after completion. Current PyTorch 2.10 Core ATen ZIP/JSON/raw-tensor archives are bounded and validated before the explicitly supported inference operator set is lowered to ONNX opset 18. Unsupported operators, dynamic symbolic shapes, non-contiguous state, training semantics, and unsupported options reject without approximation or Python execution.

Web and Desktop export copy included models and ONNX companions byte-for-byte, copy the LiteRT Wasm runtime when needed, and emit a closed version-3 `.bjsai.json` sidecar with exact byte sizes and SHA-256 values for every primary, companion, and runtime file. Runtime loading verifies every file before compilation. Cache repair detects tampering, exclusion removes only outputs no other manifest owns, paths remain contained and canonical, and the aggregate model plus ONNX companions is capped at 256 MiB. Game code opts in to inference by importing `babylonjs-editor-tools/runtime-ai-backends` once (for example in `src/scripts.ts`); without it, bundlers emit none of ONNX Runtime's ~64 MB of WebAssembly and session creation throws an error naming that import. The editor opts in itself, so Play mode always has the runtimes, and Web build plans retain the `runtime-ai` module only when project sources contain the import.

One editor-lifetime owner is shared across direct UI and MCP safety proxies. A model must be a non-empty, regular, non-symbolic-link project-contained supported file no larger than 256 MiB. Atomic create reservations enforce at most four sessions and 512 MiB of retained model bytes even under concurrent requests. Every session exposes an exact positive revision, model SHA-256, model size, runtime/conversion evidence, input/output metadata, run count, timing, busy state, and last error. Inference requires the exact current revision and every declared input exactly once; unknown/missing names, wrong tensor types, rank above eight, incompatible fixed dimensions, inconsistent element counts, unsafe integer values, unknown outputs, and configured element-limit breaches reject. Timeouts are bounded to 1–300,000 ms and returned previews to 1–100,000 values while reporting total/truncated counts. Failed run attempts record an actionable error and advance the lease. Disposal/reset require literal confirmation, reject busy sessions, and reset preserves any session whose disposal fails.

The permanent workspace visualizes real dependency layers, exact tensor edges, graph warnings, search, and 64-node pages; the File Inspector compiles the same model and opens that workspace. The eight tools are `get_runtime_ai_capabilities`, `inspect_runtime_ai_model`, `create_runtime_ai_session`, `list_runtime_ai_sessions`, `get_runtime_ai_session`, `run_runtime_ai_inference`, `dispose_runtime_ai_session`, and `reset_runtime_ai_runtime`. Their schemas are nested-closed and bounded, every tool carries all four annotations, and mutations use exact SHA-256 or revision leases. The server exposes 1,649 tools. This is portable JavaScript inference over WebGPU/WebAssembly, not Unity Sentis/Inference Engine API, serialization, native-kernel, training, or vendor binary identity.

## Unity 6.5 Windows asynchronous asset-streaming contract (#754)

Windows Electron packages embed normalized settings and the resolved plan, emit `zvibe-asset-streaming-build-plan.json`, and selectively unpack scene assets. Before scene loading, the player preserves Babylon's existing URL preprocessor and rewrites only project-contained packaged `file:` dependencies. A privileged CORS-capable `zvibe-asset://local/` handler canonicalizes the package root, rejects alternate authorities, traversal, symbolic links, non-files, multiple/invalid ranges, and unsupported methods, then serves GET/HEAD responses through the shared priority runtime with backpressure and cancellation.

Preparation binds one exact Electron profile and current project root. Probes require the latest runtime revision, read only regular non-symlink files under `assets/` or `public/`, limit one range to 64 MiB, and return only state, byte count, and SHA-256—not bytes or absolute paths. Cancel targets one queued/active request; reset requires confirmation, the latest revision, and no in-flight work. Schemas are nested-closed/bounded, all tools carry all four annotations, and the server exposes 1,631 tools to Codex CLI and Claude-compatible clients.

## Unity 6.5 hybrid direct/iterative physics contract (#750)

One version-1 scene configuration owns an exact revision, enablement, position-error bias, regularization, global/per-row impulse caps, a 1–256-row limit, and up to 64 exact angular gear couplings. Ball, distance, hinge, and lock constraints may opt into supplemental direct rows; all other native constraint families remain iterative. The shared editor/export runtime first lets Babylon/Havok perform its ordinary iterative contact and joint pass, then assembles every selected stiff and gear row into one regularized pivoted linear system and applies one bounded velocity correction. It performs no direct-solver work when no enabled row exists.

## Source control

### Ownership

- Git owns repository status, history, diffs, staging, commits, synchronization, refs, integration state, and Git conflict stages.
- Collaboration owns authenticated member identity, roles, review policy, and remote lock transport.
- Asset locks use one federated lease authority. Smart Lock policy enriches those leases; it does not create a second provider or lock namespace.
- Scene and prefab persistence owns canonical JSON. Source control may reuse the semantic merger but must not invent a second serialization model.

### Smart Lock rules

Rules are stored atomically in project-local `.babylon-editor/asset-lock-rules.json` as a versioned, bounded ordered list. Each rule has a stable id, name, enabled state, project-relative wildcard, destination branch, optional configured Git remote, and retention mode:

- `manual`: the owner may release an unexpired lease normally.
- `untilMerged`: normal release is refused until the acquisition branch path is clean and that branch's current tip is an ancestor of the exact destination revision. Ordinary lease expiry does not bypass this retained state. An authenticated administrator may use explicit force release for recovery.

The first enabled matching rule applies. Patterns support `*`, `**`, and `?`; absolute paths, traversal, option-like values, pathspec magic, line breaks, and excessive inputs are rejected. Policy mutation requires the collaboration administrator role whenever enforcement is enabled.

Acquisition under a matching rule requires:

1. a named current branch;
2. an exact current `HEAD` hash supplied by the caller;
3. an exact destination hash supplied by the caller;
4. a local destination branch or an already-known remote-tracking ref;
5. destination ancestry in current `HEAD`; and
6. a clean worktree/index state for the asset path.

Policy inspection never fetches or contacts a remote. A client must explicitly fetch through the source-control tools before relying on remote-tracking freshness. The lease retains rule identity, acquisition branch/head, destination ref/hash, asset blob hashes, and retention semantics even if the rule is later changed or deleted.
